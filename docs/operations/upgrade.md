# Upgrade and rollback

## Every upgrade

1. Read the [changelog](https://github.com/omkar-motaghare/TargetHub/blob/develop/CHANGELOG.md) for the
   target version, especially *Upgrade notes*.
2. Announce a short window. Running sessions are interrupted while the server restarts (about 30 s).
3. **Back up:** `scripts/backup.sh backups/` (see [Backup and restore](../deployment/backup.md)).
4. Update and restart:

   ```bash
   git fetch --tags && git checkout v0.2.0          # or: git pull on your release branch
   scripts/install.sh                                # reuses .env, rebuilds, waits until healthy
   # published image instead: scripts/install.sh --image ghcr.io/omkar-motaghare/targethub:0.2.0
   ```

   Database migrations run automatically when the server starts (`alembic upgrade head`).
5. Check **Admin → Overview**, sign in as a normal user, open a console on one board.
6. Upgrade agents (see below).

## Rollback

Schema migrations move forward when the server starts, so roll back by **restoring the backup taken
before the upgrade** together with the previous version:

```bash
git checkout <previous-tag>
docker compose up -d db                          # database only
scripts/restore.sh --yes backups/targethub-<timestamp>.dump
scripts/install.sh                               # starts the previous server version
```

Use the `restore.sh` of the version you return to. `alembic downgrade` exists for every migration and is
tested, but restoring the backup is the supported path because downgrades drop data that only the newer
version knows about (for example transcripts, waitlists and API tokens).

Rolling back from 0.2.0 to 0.1.0 is simpler still: the 0.1.0 volume is left untouched by the copy below,
so `docker compose down`, `git checkout v0.1.0` (commit `281f269` if you do not have the tag) and start it as before (changes made under 0.2.0 are lost).

## Upgrading agents

Agents keep working across a server upgrade, but use the agent shipped with the server version:

- **Linux / Raspberry Pi:** download `https://<server>/web/agent/targethub_agent.py`, verify its SHA-256
  (shown in a new enrollment command and in the release `SHA256SUMS`), replace
  `/opt/targethub-agent/targethub_agent.py`, then `sudo systemctl restart 'targethub-agent@*'`.
- **Windows:** replace `C:\Program Files\TargetHub\Agent\targethub_agent.py` and restart the scheduled task.
- Or revoke the agent's credential and re-enroll with a fresh command (re-runs the installer).

**Admin → Agents** shows each agent's version.

## 0.1.0 → 0.2.0 upgrade notes

**Database volume name changed.** 0.1.0 stored PostgreSQL in the Docker volume `targethub_postgres_data`
(service `postgres`); 0.2.0 uses `<project>_pgdata` (service `db`). Copy the data once **before** the first
0.2.0 start, keeping the same `POSTGRES_PASSWORD` in `.env`:

```bash
docker compose down                                        # with the 0.1.0 checkout
git checkout v0.2.0
docker volume create targethub_pgdata
docker run --rm -v targethub_postgres_data:/from:ro -v targethub_pgdata:/to alpine sh -c 'cp -a /from/. /to/'
scripts/install.sh                                         # reuses .env; migrations upgrade the schema
```

If you changed `COMPOSE_PROJECT_NAME`, replace the `targethub_` prefix accordingly. Redis and MinIO are no
longer used; remove their volumes once you are satisfied (`docker volume rm targethub_redis_data targethub_minio_data`).

Other changes to expect:

- **Everyone signs in again once.** Sessions now use 15-minute access tokens with rotating refresh tokens.
  CI should switch from passwords to personal API tokens (`thp_…`).
- **Simulated providers are off in production.** A capability without a real backend (no agent resource,
  no DD/HTTP driver) is refused instead of silently faking power or serial. Edit such targets in
  **Admin → Targets** and choose *Agent hardware*, *DD power system* or *HTTP power controller*. For demo
  servers set `ALLOW_SIMULATED_PROVIDERS=true`.
- `provider_config.transport = "agent"` is no longer needed. Agent-backed capabilities are detected from
  their agent/resource binding.
- **Roles:** existing users keep *admin* or *user*; the new *viewer* role is read-only.
- `/metrics` needs `Authorization: Bearer $METRICS_TOKEN` (generated by the installer) or an admin token.
- The legacy dashboard (`/legacy-dashboard`, `/web/*.js`) is gone; `/dashboard` redirects to `/app`.
- Upgrade agents to 0.2.0 to get buffered serial, concurrent operations and Windows support.
